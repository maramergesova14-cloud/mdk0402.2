# Требования к системе «Электронный журнал группы»

## 1. Назначение

Система предназначена для централизованного хранения и обработки сведений о студентах, учебных предметах, оценках и посещаемости. Основные пользователи — администратор, преподаватель и студент. Роли описывают целевую модель и должны быть реализованы в приложении отдельно.

## 2. Проблема и цель

При ведении учёта вручную сложно быстро найти сведения, проверить историю изменений и подготовить сводные данные. Цель проекта — спроектировать веб-приложение, которое уменьшает повторный ввод информации и обеспечивает единый формат хранения.

## 3. Пользовательские роли целевой версии

| Роль | Предполагаемые возможности |
|---|---|
| Администратор | Управление справочниками и учетными записями, контроль корректности данных |
| Преподаватель | Просмотр учебных групп и предметов, внесение оценок и посещаемости в рамках назначенных занятий |
| Студент | Просмотр собственных оценок и посещаемости |

Эта таблица является проектным требованием. Если в текущей версии нет авторизации и проверки прав, такие ограничения пока не обеспечиваются.

## 4. Функциональные требования

- **FR-01:** система хранит сведения о студентах.
- **FR-02:** система хранит сведения об учебных предметах.
- **FR-03:** система позволяет создавать и просматривать оценки.
- **FR-04:** каждая оценка связана с существующим студентом и предметом.
- **FR-05:** система хранит дату оценки и необязательный комментарий, если эти поля предусмотрены моделью.
- **FR-06:** система хранит сведения о посещаемости, включая студента, предмет, дату и статус.
- **FR-07:** пользователь может получать записи через API в структурированном формате.
- **FR-08:** администратор может работать с настроенными моделями через административную панель.
- **FR-09 (целевая доработка):** система аутентифицирует пользователя и применяет права согласно роли.
- **FR-10 (целевая доработка):** система рассчитывает средний балл на основании действующих оценок.
- **FR-11 (целевая доработка):** система формирует сводные отчёты за выбранный период.

## 5. Нефункциональные требования

- данные должны храниться в реляционной базе данных;
- обязательные поля и связи должны проверяться;
- API должен возвращать понятные статусы HTTP и сообщения об ошибках;
- секреты и пароли не должны попадать в публичный репозиторий;
- приложение должно запускаться по документированной инструкции;
- резервное копирование должно быть предусмотрено для среды эксплуатации;
- интерфейс и сообщения должны быть понятны русскоязычному пользователю.

## 6. Ограничения и допущения

- точные поля моделей следует сверять с кодом приложения;
- в учебной среде допустимы синтетические данные;
- доступность через интернет не подразумевается автоматически;
- авторизация, ролевые ограничения, расчёт среднего балла и отчёты считаются выполненными только после отдельной реализации и тестирования.

## 7. Критерии приёмки

1. Можно создать и получить студента и предмет.
2. Можно создать оценку с существующими связями.
3. Можно создать запись посещаемости.
4. Некорректные данные обрабатываются без необъяснимого сбоя.
5. Сохранённые сведения доступны после повторного запроса.
6. Документированы ограничения текущей версии.
7. Если внедрены роли и дополнительные функции, для них есть отдельные успешные тесты.
