# Проектирование REST API

## 1. Назначение

API предоставляет структурированный доступ к данным электронного журнала. Ниже перечислены основные ресурсы. Точные маршруты, поля и методы необходимо сверять с настройками маршрутизации и сериализаторами текущей версии приложения.

## 2. Ресурсы

| Ресурс | Назначение |
|---|---|
| `/api/students/` | Получение списка и операции со студентами |
| `/api/subjects/` | Получение списка и операции с предметами |
| `/api/grades/` | Просмотр и изменение оценок |
| `/api/attendance/` | Просмотр и изменение посещаемости |

Для конкретной записи обычно используется маршрут с идентификатором, например `/api/students/1/`, если такой маршрут зарегистрирован роутером.

## 3. Типовые методы HTTP

| Метод | Назначение | Ожидаемый смысл результата |
|---|---|---|
| GET | Получить список или одну запись | Возвращаются данные |
| POST | Создать запись | Возвращается созданная запись |
| PATCH | Частично изменить запись | Меняются переданные поля |
| PUT | Полностью обновить запись | Обновляются поля ресурса согласно API |
| DELETE | Удалить запись | Запись удаляется, если это допускают ограничения |

Фактический набор методов зависит от зарегистрированных представлений и маршрутов.

## 4. Пример структуры данных

Пример запроса создания оценки приведён для иллюстрации; названия полей должны совпадать с сериализатором приложения.

```json
{
  "student": 1,
  "subject": 1,
  "value": 5,
  "date": "2026-10-26",
  "comment": "Контрольная работа"
}
```

Пример записи посещаемости:

```json
{
  "student": 1,
  "subject": 1,
  "date": "2026-10-26",
  "status": "present"
}
```

## 5. Коды ответа

- **200 OK** — запрос выполнен успешно;
- **201 Created** — запись создана;
- **204 No Content** — операция выполнена без тела ответа;
- **400 Bad Request** — данные не прошли проверку;
- **401 Unauthorized** — требуется аутентификация, если она настроена;
- **403 Forbidden** — действие запрещено правами пользователя, если проверка прав реализована;
- **404 Not Found** — ресурс не найден.

Не каждый код обязательно используется во всех представлениях проекта. Проверять следует фактический ответ API.

## 6. Безопасность API

Для целевой версии рекомендуется:
- включить аутентификацию;
- проверять разрешения на каждом изменяющем запросе;
- ограничивать доступ студента собственными данными;
- ограничивать преподавателя назначенными группами и предметами;
- проверять типы и диапазоны входных значений;
- не использовать реальные персональные данные в публичных примерах.

Если в текущей версии API разрешения не ограничивают доступ, нельзя считать его безопасным для публикации реальных данных.

## 7. Проверка API

Основные проверки: получение списка, создание записи, изменение, удаление тестовой записи, проверка несуществующего идентификатора, передача неверных данных и проверка связей между студентом и предметом.
